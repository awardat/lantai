## 〇、对话内容总结（本次备忘的缘起）

1. **CI/CD 是什么**：持续集成（CI）+ 持续交付/部署（CD）。CI = 每次代码提交自动"构建+测试"把关；CD = 让代码始终处于可发布状态（交付，人工批准上线）或自动上线（部署）。
2. **发布策略**：滚动更新（逐台替换）、蓝绿（双环境切流量，秒级回滚）、金丝雀（小流量灰度观察后全量）。
3. **AI 与 CI/CD 的关系**：AI 辅助开发 = "CI/CD 流程骨架 + AI 执行引擎 + 人类审批门"（Human-in-the-loop）；完整"AI 驱动 CI/CD" = 门禁判定与修复也交给 AI（业界探索中）。传统 CI/CD 是确定性工具流水线；AI 生成式输出需人工确认。

## 一、核心概念与术语

| 术语 | 含义 |
|------|------|
| **持续集成 CI** | 每次代码提交（push/PR）自动触发：拉依赖 → Lint → 单测/集成测试 → 构建制品。尽早暴露集成问题 |
| **持续交付 CD（Delivery）** | 代码始终"可发布"：制品自动部署到测试/预发环境，生产发布保留**人工审批** |
| **持续部署 CD（Deployment）** | 在交付基础上，全部门禁通过后**自动部署生产**，无人干预 |
| **制品 Artifact** | 构建产物（jar/wheel/exe/镜像/npm 包），带版本号+哈希，存入制品库 |
| **质量门禁** | 流水线中硬性检查点（测试/扫描/规范），失败即阻塞并通知 |
| **环境** | 开发 dev → 测试 test → 预发 staging → 生产 prod；同一制品逐环境推进 |
| **回滚** | 切回上一版本制品重新部署（数据库迁移需向下兼容） |

**一句话**：CI 保证"代码始终是好的"，CD 保证"好的代码能快速、安全、可回滚地上线"。

## 二、方法与实践

### 2.1 持续集成要点
- **小步提交**：频繁、小粒度合并（每天多次），冲突和集成问题早暴露
- **主干开发 / 特性分支 + PR**：PR 触发 CI + 代码评审（Code Review）
- **测试金字塔**：大量单元测试 + 适量集成测试 + 少量端到端测试
- **构建可复现**：锁版本（lockfile）、同一制品全环境一致

### 2.2 持续交付/部署要点
- **制品化**：一次构建，多处部署（Build once, deploy many）
- **环境一致性**：配置外置（环境变量/配置中心），代码不含环境差异
- **发布策略**：滚动 / 蓝绿 / 金丝雀（见第六节）
- **自动化冒烟**：部署后自动健康检查/冒烟测试，失败自动回滚
- **数据库迁移**：与代码发布配套，向前兼容（expand-migrate-contract）

### 2.3 质量与安全门禁
- 单元/集成/端到端测试通过
- 静态扫描（SonarQube/SAST）、依赖漏洞扫描（SCA）、容器镜像扫描
- 规范检查（Lint）、覆盖率阈值、性能基线
- **门禁不过 = 阻塞发布**（硬性，不靠自觉）

## 三、标准流程（端到端）

```
开发者提交代码（特性分支/主干）
   │
   ▼
① CI 流水线：Lint → 单测 → 集成测试 → 安全扫描 → 构建制品 v1.2.3
   │        （任一失败 → 阻塞 + 通知修复）
   ▼
② 制品入库：Nexus/Artifactory/Harbor（版本 + SHA 哈希，可追溯）
   │
   ▼
③ 代码评审（PR Review）通过 → 合并主干
   │
   ▼
④ CD 部署：
   测试环境（自动）→ 预发环境（自动）→ 生产环境（审批门/自动）
   │
   ▼
⑤ 发布策略执行：滚动 / 蓝绿 / 金丝雀
   │
   ▼
⑥ 部署后：自动冒烟 + 监控观察（指标/日志/告警）
   │
   ▼
⑦ 异常 → 一键回滚（切旧制品）；正常 → 发布完成 + 变更记录归档
```

## 四、主要角色与职责

| 角色 | 核心职责 |
|------|----------|
| **开发者** | 写代码、单测、自测；提交符合规范；处理 CI 失败 |
| **技术负责人 / Reviewer** | PR 代码评审（质量/架构/安全），把关合并 |
| **CI/CD 工程师 / DevOps** | 搭建维护流水线、制品库、环境编排；保障构建/部署稳定 |
| **QA / 测试** | 测试策略、验收用例；测试环境验证 |
| **发布经理 / 变更经理** | 生产发布排期、审批、变更记录、发布窗口 |
| **运维 / SRE** | 生产环境、监控告警、容量、故障处置与回滚执行 |
| **安全工程师** | 安全门禁（扫描策略）、漏洞修复跟踪、合规（审计留痕） |

> 小团队可一人多角，但**职责分离**（开发者不自行批准生产发布）是风险控制底线。

## 六、发布策略详解

| 策略 | 做法 | 优点 | 注意 |
|------|------|------|------|
| **滚动更新** | 逐台替换旧实例（先新后旧逐步切换） | 零停机、实现简单 | 新旧版本短暂共存，需兼容 |
| **蓝绿** | 蓝/绿两套环境，流量整体切换 | **秒级回滚**（切回旧环境） | 资源翻倍 |
| **金丝雀** | 先 5%~10% 流量到新版，观察指标后渐进全量 | 风险最小，适合核心系统 | 需要流量控制与指标对比 |
| **直接替换 + 回滚预案** | 全量替换，异常时切回旧制品 | 最简单 | 回滚=重新部署旧版，耗时较长 |

> 选择依据：系统重要性、资源成本、回滚速度要求、发布频率。

## 七、回滚与事故处理

1. **回滚原则**：先恢复服务，再查根因（Rollback first, debug later）
2. **回滚方式**：蓝绿切流量 / 金丝雀放量回退 / 重新部署上一版本制品
3. **数据兼容**：数据库迁移需向前兼容（旧代码可读写），回滚才安全
4. **事后**：事故复盘（时间线/根因/改进项）、补自动化测试防回归、变更记录归档
5. **灰度放量失败标准**：错误率/延迟/业务指标超过阈值即自动或人工回退

## 八、落地检查表（新建项目搭 CI/CD）

- [ ] 版本控制就绪，分支策略明确（主干开发 or Git Flow）
- [ ] CI 流水线：Lint → 单测 → 构建制品 → 上传制品库
- [ ] 质量门禁：测试通过、覆盖率阈值、安全扫描
- [ ] 制品版本化（语义化版本 + 哈希），可追溯
- [ ] 环境划分（test/staging/prod）与配置外置
- [ ] 部署自动化（脚本/Ansible/K8s），生产发布含审批门
- [ ] 发布策略选定（滚动/蓝绿/金丝雀）与回滚预案
- [ ] 部署后冒烟测试 + 监控告警（指标/日志）
- [ ] 变更记录与审计留痕

## 九、AI 与 CI/CD（本次讨论结论存档）

| 形态 | 描述 | 现状 |
|------|------|------|
| **AI 辅助开发（当前主流）** | CI/CD 流程骨架 + AI 执行引擎（写码/测试/文档）+ 人类审批门 | 成熟可用（本项目即此模式） |
| **AI 驱动 CI/CD** | 门禁判定与修复也由 AI 完成，人只出现在需求与生产发布决策点 | 业界探索中，可靠性存疑 |

**核心差异**：传统 CI/CD 是确定性工具流水线（同输入必同输出、机器门禁）；AI 生成式输出需人工确认，故现阶段"人机协作流水线"是落地形态。
