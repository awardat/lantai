## 一、总体评价

**完成度高、架构清晰、文档完备**。代码与文档高度一致，需求池 16 个 P0 项均有对应实现，扩展点（VectorStore 抽象、Retriever 组合点、llm 流式参数预留）为后续迭代留好了接口。整体质量在"演示产品"定位下属**良好**，但存在 **1 个严重 bug**（云端 API Key 未解密）和 **1 个显著性能问题**（async 端点阻塞事件循环），建议在进入下一版迭代前修复。

## 二、问题清单（按严重度分级）

### 🔴 严重（影响已声明功能正常运行）

**S1. 云端 API Key 未解密——所有真实 AI 调用路径发送的是加密后的密文**

`get_ai_config()` 从 `settings.ai_config` 读取并返回存储值，而 `put_ai` 保存时对 `api_key` 做了 `security.encrypt_api_key()` 加密（`x1:` 前缀的 XOR+base64）。但所有实际调用 AI 的路径都直接用 `get_ai_config()` 的返回值构造 `AiItem`，**从未调用 `decrypt_api_key`**：

| 调用位置 | 代码 | 问题 |
|----------|------|------|
| `routers/chat.py:45-46` | `cfg = store.get_ai_config()["chat"]; item = AiItem(**cfg)` | api_key 为 `x1:...` 密文 |
| `retriever.py:16-17` | `cfg = st.get_ai_config(); AiItem(**cfg["embedding"])` | 同上 |
| `pipeline.py:38` | `cfg = st.get_ai_config()["image"]` → `_vision_describe` | 同上 |
| `pipeline.py:49` | `cfg = st.get_ai_config()["pdf_image"]` → `_ocr_pdf` | 同上 |
| `pipeline.py:81` | `AiItem(**st.get_ai_config()["embedding"])` | 同上 |

唯一调用了 `decrypt_api_key` 的地方是 `routers/settings.py:104`（测试连接 `test_ai`）。

**后果**：使用 Ollama（默认，api_key 为空）时正常；一旦配置云端 Provider 并填入 API Key 保存后，问答/embedding/图片解析/OCR 全部会携带 `Bearer x1:...`（密文）而非真实 Key，收到 401 鉴权失败。用户会误以为"API Key 填错了"。自测大概率因全程用 Ollama 而未暴露。

---

### 🟠 高（影响演示体验）

**H1. 所有路由端点声明为 `async def`，但内部调用阻塞式同步 I/O，阻塞事件循环**

全部 router 方法是 `async def`，在 FastAPI 事件循环上执行。但内部调用的是同步阻塞操作：

- `routers/chat.py:32` `retriever.retrieve()` → SQLite 查询 + numpy 全表计算（CPU 密集）
- `routers/chat.py:58` `llm.chat()` → `httpx.Client`（同步阻塞 HTTP，最长 120s）
- `routers/settings.py:108` `llm.list_models()` → 同步阻塞 HTTP
- `routers/docs.py:93-110` `preview_document()` → 同步文件读取 + pypdf/python-docx 解析
- 全部 `store.*` 调用 → 同步 SQLite I/O

**后果**：单用户提问时，若 LLM 响应需 30s，整个服务在此 30s 内完全不响应任何请求——包括前端的文档状态轮询（`GET /api/docs` 每 2s 一次），浏览器会显示"等待响应"。对现场演示体验影响明显。

> 修复方向：将端点改为普通 `def`（FastAPI 自动丢入线程池），或改用 `httpx.AsyncClient` + `await`。

### 🟡 中（边界场景 / 约束符合度）

**M1. AI 配置 PUT 支持部分提交，但 `save_ai_config` 是整覆写——未提交的槽位丢失已存值**

`store.py:234-236` `save_ai_config` 直接用传入的 `cfg` 替换整个 `ai_config` JSON：

```python
def save_ai_config(self, cfg):
    clean = {k: v for k, v in cfg.items() if k in AI_CONFIG_KEYS}
    self.set_setting("ai_config", json.dumps(clean, ensure_ascii=False))
```

`routers/settings.py:78-92` `put_ai` 只处理 `body.items` 中包含的 key，未提交的 key 不会进入 `incoming`，因此不会被保存。

API 说明文档 §4.3 明确写"**可只提交部分**"。但若通过 API 只提交 `{"items": {"chat": {...}}}`，其余 6 个槽位之前保存的定制值会丢失（下次读取时回退到默认值）。

> 从前端 UI 提交不受影响（`app.js:380` 总是收集全部 7 个 key）。

**M2. `lantai.spec` 位于工作区根目录，违反 AGENTS.md 硬性约束**

AGENTS.md 明确："**工作区根目录只允许放 `AGENTS.md` 与 `README.md` 两个文件**"。实际根目录还存在 `.gitignore`（标准 git 文件，可视为豁免）和 `lantai.spec`（PyInstaller 构建配置，应归入 `scripts/` 或 `backend/`）。

**M3. `.gitignore` 中 `*.spec` 规则与 `lantai.spec` 需入库相冲突**

`.gitignore:18` 有 `*.spec`（归类于"发布产物"），但 `lantai.spec` 是构建源文件应纳入版本管理。当前若未 force-add 则新克隆者拿不到构建脚本；若已 force-add 则该规则产生混淆。应改为 `!lantai.spec` 否定规则或移到子目录后调整路径。

### 🟢 低（文档与代码不一致 / 细节）

**L1. 数据库设计文档列出的 3 个索引，代码只建了 1 个**

`数据库设计文档.md:85-87` 声明：
- `idx_chunks_document` ✅ `store.py:61` 已建
- `idx_docs_status` ❌ 代码未建
- `idx_tokens_revoked` ❌ 代码未建

演示规模下无性能影响，但文档与实现不一致。

**L2. 数据库设计文档列出的 `ai_key_salt` 键在代码中不存在**

`数据库设计文档.md:61` 定义 `ai_key_salt` 为"API Key 的加密盐"，但代码 `security.py:108-119` 实际用 `session_secret` 派生 XOR 密钥，从未创建或使用 `ai_key_salt`。

**L3. 安全方案文档称"XOR+HMAC 封装"，实现只有 XOR，无 HMAC 完整性校验**

`数据库设计文档.md:65`："以 `session_secret` 派生密钥做 XOR+HMAC 封装"。
`security.py:122-142`：实际只有 XOR + base64，没有 HMAC。封装格式 `x1:<base64>` 中不含 MAC 校验码。对演示级防护无实质影响，但描述不准确。

**L4. 技术对接方案 §6.3 的配置接口路径与实际实现不一致**

| 技术对接方案.md 写的 | 实际实现 | API说明文档.md 写的 |
|---------------------|----------|---------------------|
| `/api/tokens` GET/POST | `/api/settings/tokens` | `/api/settings/tokens` ✅ |
| `/api/tokens/{id}` DELETE | `/api/settings/tokens/{id}` | `/api/settings/tokens/{id}` ✅ |
| `/api/system/info` GET | `/api/settings/system/info` | `/api/settings/system/info` ✅ |

技术对接方案.md 的路径缺 `/settings` 前缀，API说明文档.md 已修正。两份文档间存在不一致。

**L5. 原型设计方案写"答案区（Markdown 渲染）"，实际为纯文本**

`原型设计方案.md:29`："答案区（Markdown 渲染）"。
`app.js:177-178`：用 `textContent` 渲染答案，Markdown 语法原样显示（如 `**粗体**` 显示为字面量）。未引入 Markdown 解析库（符合"无构建/无重依赖"原则），但与设计文档描述不符。

**L6. `import_docs.py` 默认导入 `docs/` 目录——会导入项目设计文档而非演示文档**

`import_docs.py:20` 默认目录为 `docs/`，使用 `rglob("*")` 递归导入。当前 `docs/` 存放的是项目文档（PRD、技术对接方案等），运行后会把这些设计文档也灌入知识库。AGENTS.md 对 `docs/` 的定位也有矛盾：目录结构部分写"需求调研/方案设计"，后文又写"用户演示文档目录（用户提供）"。

**L7. `Store()` 每次实例化都执行 `executescript(_SCHEMA)`**

`store.py:89-90`：构造函数每次都跑 `CREATE TABLE IF NOT EXISTS ...`。而 `chat.py`、`docs.py`、`settings.py`、`pipeline.py`、`security.py`、`main.py` 各自创建 Store 实例。`IF NOT EXISTS` 使其无害，但属冗余开销。

**L8. `@app.on_event("startup")` 已被 FastAPI 标记为废弃**

`main.py:28`：应迁移至 `lifespan` 上下文管理器。当前仍可运行但会输出 deprecation warning。

**L9. embedding 模型更换后无维度兼容处理**

若用户中途更换 embedding 模型（如 bge-m3 1024 维 → 其他模型 768 维），新旧切片向量维度不同，`store.search()` 的 `np.vstack` 会在维度不一时报错。无检测/提示/迁移机制。演示场景下用户需手动删除旧文档重传，可接受但值得在错误提示中说明。

### ℹ️ 提示（非问题，供参考）

- **前端 `onclick` 内联调用依赖后端文件名净化防 XSS**：`app.js:143` 用 `esc(d.name)` + `.replace(/'/g,"\\'")` 构造内联 JS，因 `esc()` 不转义引号，安全性实际依赖后端 `filetype.sanitize_filename` 已去除 `"<>\|*?/\\` 等字符。建议后续改为 `data-*` 属性 + 事件监听以做纵深防御。
- **会话仅存内存**：后端重启后所有配置会话失效，需重新验证。API说明文档 §6.4 已明确说明，属设计决策。
- **`docs/03-增长迭代/` 与 `docs/04-风控管理/` 目录不存在**：AGENTS.md 标注为"预留"，不创建是合理的。
- **版本号一致性 ✅**：`config.py:12`、`README.md:3`、`requirements.txt:1`、`release/` 目录名、全部文档——版本号均为 `0.1.1`，完全同步。
- **AGENTS.md 根目录文件约束**：除 `lantai.spec`（M2）外，其余合规。

## 三、优点

1. **架构分层清晰**：config / store / security / llm / embeddings / chunker / filetype / pipeline / retriever / routers 各司其职，耦合度低，扩展点注释明确（如 `retriever.py` 标注 rerank/hybrid 组合点）。
2. **错误处理完善**：`llm._friendly_error()` 将连接/鉴权/超时/模型不存在等场景统一映射为中文提示含解决建议；前端 `api()` + `toast()` 统一兜底；后端三个全局异常处理器保证不漏白屏。
3. **安全基线合理**：PBKDF2 加盐哈希 + `hmac.compare_digest` 防时序攻击；失败锁定；HTTP-only Cookie；API token SHA-256 存储不留明文；文件名净化防路径穿越；扩展名白名单 + 大小限制。
4. **文档体系规范**：7 份文档表头信息齐全、来源标注清晰、需求 ID 可追溯、验收标准明确，符合 AGENTS.md 要求的"docs-sample 样例风格"。
5. **前后端契约一致**：统一 `{code, message, data}` 响应；前端 `api()` 严格按契约解析；错误码与 API 文档对应。
6. **部署形态考虑周到**：`config.py` 区分源码/冻结模式路径；`run.py` 自动开浏览器；`lantai.spec` 打包前端静态资源 + uvicorn hidden imports。
