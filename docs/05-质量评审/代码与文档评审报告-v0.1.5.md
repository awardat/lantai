## 二、本次新发现问题（v0.1.3~0.1.5 引入或残留）

### 🟡 中危

**N-M1. SSE 流式端点对无效 `conversation_id` 处理不一致——先发 sources 再断流，无干净 404/error**

`routers/chat.py` 的 `chat_stream` 中，`_do_retrieve`（行 101）在返回 `StreamingResponse` 之前的端点体内执行，检索失败能正确返回 502。但 `_build_messages`（行 119，内含 `_history_messages` 的会话存在性校验）在生成器 `gen()` 内、且在 `yield _sse({"type":"sources",...})`（行 117）**之后**执行。

后果：当 `conversation_id` 指向已删除的会话时——
- 客户端先收到 `sources` 事件；
- 随后 `_history_messages` 抛 `HTTPException(404)`，该异常在生成器内、且不在行 121-129 的 `try` 内 → 流被截断，**不发送 `error` 事件**；
- 客户端表现为：有来源、无答案、无错误提示、流静默结束。

对比：非流式 `chat`（行 75）在端点体内调 `_build_messages`，能正确返回 404 JSON。两条路径行为不一致。

> 修复方向：在 `chat_stream` 端点体内（返回 StreamingResponse 之前）预校验 `conversation_id` 存在性；或将 `_build_messages` 调用提到首个 `yield` 之前。

**N-M2. 预置供应商 `deepseek-v4-flash` 模型名不符合 DeepSeek 实际模型命名约定——用户用预置值大概率报"模型不存在"**

`vendors.py:27/54` 与 `README.md:60/67` 将 DeepSeek / OpenCode Go 的推荐 chat 模型设为 `deepseek-v4-flash`。DeepSeek 官方 API 的模型命名约定为 `deepseek-chat` / `deepseek-reasoner` / `deepseek-coder` 等，不含"v4-flash"式命名（"flash"更接近 Gemini 约定）。

后果：用户在设置页选择"DeepSeek"供应商预置项、填入真实 API Key 后，问答/解析会因模型名不存在而失败（404 或 model not found），与预置"开箱即用"的预期相悖，且容易被误判为"API Key 填错"。

> 说明：本项目时间线为 2026-08，无法完全排除 DeepSeek 届时新增该模型名的可能；但当前命名与已知约定明显不符，**建议核对实际 DeepSeek 模型清单后修正**（如改回 `deepseek-chat`，CH-009 的调整值得复核）。

**N-M3. 技术对接方案 §9.2 安全描述"uuid 重命名存储"与实现不符——夸大了上传安全**

`技术对接方案.md:259`："上传：扩展名白名单、大小限制、文件名净化（**uuid 重命名存储**）、目录禁执行"。
实际 `filetype.py:22-26` `sanitize_filename` 只做字符净化并**保留原始文件名**，存储路径为 `uploads/<doc_id>/<净化后原名>`，并未用 uuid 重命名。

后果：安全文档描述与实现不一致，可能误导评审者高估防护。现有方案（per-doc_id 目录 + 文件名净化）已能防路径穿越，并非不安全，但"uuid 重命名"不属实。

> 修复方向：将该句改为"文件名净化（去除路径分隔符与控制字符，按 doc_id 分目录存储）"。

### 🟢 低危

**N-L1. `security.py` docstring 仍称"XOR+HMAC 封装"，实现无 HMAC（L3 残留）**

`security.py:2`："AI 配置中 API Key 的存储加密（演示级：XOR+HMAC 封装…）"。实际 `encrypt_api_key`/`decrypt_api_key`（行 122-142）只有 XOR + base64，无 HMAC 完整性校验。数据库设计文档已修正，本文件漏改。

**N-L2. API 说明文档示例版本号与页脚过期**

- `API说明文档.md:308` 系统信息示例 `"version": "0.1.4"`（应用已 0.1.5）；
- `API说明文档.md:396` 页脚"API 说明 V1.0（与应用 **0.1.1** 同步）"，而文档头标 V1.4（对应 0.1.5）。

**N-L3. 数据库设计文档页脚版本号过期**

`数据库设计文档.md:134` 页脚"数据库设计 **V1.0**"，文档头标 V1.2。另 `:62` `app_version` 说明写"版本号（0.1.2）"为首次写入值，历史准确但可补注"后续版本启动会更新为当前 APP_VERSION"。

**N-L4. 技术对接方案多处未同步 0.1.3~0.1.5 新增模块与接口**

- §3.2 模块表未含 `vendors.py`、`routers/conversations.py`；
- §5 数据库概要表未含 `conversations`/`messages`；
- §6 API 表未含 `/api/chat/stream`、`/api/conversations*`、`/api/settings/vendors`（API 说明文档已补，两文档不同步）；
- §3.2 `config.py` 行仍写"版本（0.1.1）"。

> 注：§7.1/7.2 已正确标注"0.1.5 已实现"，这部分同步做得好。

**N-L5. 版本记录中 0.1.4 与 0.1.5 均标"当前版本"**

`版本记录.md:32` 0.1.4 标"当前版本（含修订）"，`:33` 0.1.5 也标"当前版本"。应仅 0.1.5 为当前版本，0.1.4 改为"保留可回滚"。

**N-L6. AGENTS.md 状态段跳过 0.1.4**

AGENTS.md「状态」段自 0.1.3 直接跳到 0.1.5，无 0.1.4 条目（版本记录与需求变更记录均有 0.1.4：OpenCode Go 供应商、测试功能、日志、503 通用化、窗口尺寸修订）。状态段与版本记录不同步。

**N-L7. `main.py` `_setup_file_logging` 存在冗余重复代码**

`main.py:51-52` 取 root 并检查 FileHandler，行 52 命中则 return；行 65-66 又取一次 root 并重复同一检查。第二处检查在已 return 未触发的分支内必然为假，属冗余。功能无害，代码可读性差。

**N-L8. `chat` 端点重复读取 chat 配置（双重解密）**

`routers/chat.py:41` `_build_messages` 内读 `store.get_ai_config()["chat"]` 取 system_prompt，`:76` 端点内再读一次取 `AiItem`。单次问答触发两次 `get_ai_config`（含 JSON 解析 + api_key 解密），其中第一次的 api_key 解密属浪费（只需 prompt）。演示规模无感，可合并为一次读取。

**N-L9. 会话无法重命名，标题恒为"新对话"——多会话时难以区分**

`conversations.py` 仅提供创建/列表/删除，无重命名接口；前端 `app.js:210/246` 创建时 title 恒传"新对话"。下拉框（`app.js:184`）对全部会话显示"新对话"，仅靠 `对话 #id` 区分。多会话场景体验下降。非 bug，属功能缺口。

**N-L10. SQLite 外键未启用，级联靠应用代码**

`store.py` 未执行 `PRAGMA foreign_keys=ON`，`messages.conversation_id`、`chunks.document_id` 的 FK 约束（数据库设计文档标注）实际不生效；级联删除由 `delete_document`/`delete_conversation` 在应用层事务内完成。演示场景可接受，但与文档"FK"标注有出入。

**N-L11. 前端内联 `onclick` 防 XSS 仍依赖后端文件名净化（纵深防御缺口，同 v0.1.1 提示）**

`app.js:159` 以 `esc(d.name).replace(/'/g,"\\'")` 构造 `onclick="deleteDoc(id, 'name')"`。`esc` 不转义引号，安全性依赖后端 `sanitize_filename` 已去除 `"'<>\|*?/\\` 等字符。建议后续改为 `data-*` 属性 + 事件监听做纵深防御。

**N-L12. SSE 同步生成器占用线程池工作线程整条流时长**

`chat_stream` 为 `def` 端点 + 同步 `gen()` + `httpx.Client.stream`，Starlette 在线程池执行，整条流（可达 120s）占用一个 worker。uvicorn 默认线程池 40，单用户演示无碍，多并发流式可能耗尽。可延后。

## 三、优点

1. **0.1.2 修复彻底、可验证**：每项修复都能在代码中找到明确证据，注释标注了修复编号（如 `store.py` "S1 修复""M1 修复""L9 修复"），便于追溯。
2. **SSE 实现规范**：事件协议清晰（sources → delta* → done / error），设置 `X-Accel-Buffering: no` 防 nginx 缓冲，前端 fetch + ReadableStream 打字机渲染，错误经 `error` 事件传达（除 N-M1 的边界场景外）。
3. **对话历史设计干净**：schema 用 `user_version` 迁移；`recent_messages` 取最近 6 条拼入上下文；回答后入库；前端会话切换/删除/历史渲染完整。
4. **供应商预置实用**：8 个供应商（国产优先）+ 能力声明 + 自动填充 + 不匹配提示 + 测试回填模型，形成完整配置闭环。
5. **变更管理流程化**：需求变更记录（CH-001~CH-015）+ 版本记录双文档，先登记后实施，可追溯；README 版本明细下沉到版本记录，职责清晰。
6. **文档体系持续完善**：API 说明文档已补 SSE/对话/供应商接口；数据库设计文档已补新表与新索引；技术对接方案 §7 已标注实现状态。
