## 三、本次新发现问题

### 🟠 高危

**H1. `pipeline.py:121` `_ocr_pdf` 函数内 `doc_id` 未定义——NameError（扫描件 + 视觉模型不可用场景必现）**

`_ocr_pdf(file_path: Path, st: Store)` 签名无 `doc_id` 参数，函数体内亦无 `doc_id` 局部变量，但行 121 调用 `_vision_describe(..., doc_id=doc_id)`：

```python
def _ocr_pdf(file_path: Path, st: Store) -> str:
    ...
    for page_no, data, mime in images:
        text = _vision_describe(cfg, data, mime, "...", slot="pdf_image", doc_id=doc_id)  # doc_id 未定义
```

对比同文件 `_ocr_pdf_pages`（行 93）签名含 `doc_id` 参数、`_describe_inline_images`（行 69）含 `doc_id`——唯 `_ocr_pdf` 漏了。

**触发路径**：`pipeline.py:55` `return _ocr_pdf(file_path, st), "pdf_image"`——当 pdf_text 分支中所有页均为图片页且 `_ocr_pdf_pages` OCR 返回空（视觉模型不可用）导致 `text < PDF_TEXT_MIN_CHARS` 时调用 `_ocr_pdf`。

**后果**：扫描件 PDF + 视觉模型不可用时，本应 failed + 中文"视觉模型不可用"提示，实际抛 `NameError: name 'doc_id' is not defined`，被 `process_document` except 捕获后 `set_document_status(failed, "name 'doc_id' is not defined")`——用户看到英文技术错误，违反 R013 友好中文提示；且这是代码 bug 而非用户环境问题，误导排查方向。

> 正常路径（视觉模型可用，OCR 成功）不触发，故定高危而非严重。0.1.11 自测用 Mock AI（视觉可用），未覆盖"视觉不可用"分支，故未暴露。
> 修复：`_ocr_pdf` 签名加 `doc_id: int | None = None`，`pipeline.py:55` 调用处传 `doc_id=doc.get("id")`。

**H2. `requirements.txt` 缺 pdfminer.six——0.1.8 引入但未声明依赖，源码部署 PDF 解析必失败**

`filetype.py:87-88` `from pdfminer.high_level import extract_pages` / `from pdfminer.layout import ...`，而 `requirements.txt` 仅含：fastapi/uvicorn/pydantic/httpx/python-multipart/numpy/pypdf/pillow/python-docx，**无 pdfminer.six**。

**后果**：新机器按 README「源码运行」`pip install -r requirements.txt` 后，上传任意 PDF 触发 `pdf_text_layers` → `ImportError: No module named 'pdfminer'`，PDF 解析全部失败（txt/md/docx/图片不受影响）。编译版因 PyInstaller 静态分析能发现该 import 且构建机已装，故编译版可用（0.1.8 release 体积跳增 11MB 印证已打包）——但源码部署形态不可用，与 README 声明的源码运行方式矛盾。

> 修复：requirements.txt 增加 `pdfminer.six>=20240722`（或合适版本下限），并同步 build-requirements.txt（已含 `-r requirements.txt`，自动继承）。

**H3. `config.py` APP_VERSION="0.1.10" ≠ 实际 0.1.11——版本号未同步，违反硬性约束**

`config.py:12` `APP_VERSION = "0.1.10"`，而版本记录、AGENTS.md 状态段、release 目录、README 均为 **0.1.11**。0.1.11（扫描件修复）发布时漏升 config.py。

**后果**：
- `GET /api/settings/system/info` 返回 `version: "0.1.10"`，前端「关于」页显示 0.1.10；
- README 显示 0.1.11；
- 违反 AGENTS.md「版本号同步更新于代码、README 与相关文档」硬性约束。

> 修复：`config.py:12` 改为 `"0.1.11"`。

### 🟡 中危

**M1. `_setup_file_logging` 无幂等提前 return——reload 场景重复创建 FileHandler 致文件句柄泄漏**

`main.py:44-85` 注释自称"单点挂载（N-L7：挂载逻辑幂等，无冗余提前返回）"，但实际函数体无 `if any(isinstance(h, logging.FileHandler) for h in root.handlers): return` 的提前返回（对比 `agent_log.py:23-24` 有此幂等检查）。每次调用都新建 `fh = logging.FileHandler(log_path)`（打开文件句柄），仅以 `if not any(... root.handlers): root.addHandler(fh)` 防重复挂载——但 `fh` 对象已创建，未挂载的 `fh` 未 `close()`，泄漏一个文件句柄。

正常启动（lifespan 仅一次）无影响；uvicorn `--reload` 热重载场景会重复调用，累积泄漏。演示场景一般不开 reload，定中危。

> 修复：函数开头加幂等提前 return，或将 `fh` 创建移至 `if not any(...)` 分支内。

**M2. 数据库设计文档 §5「预留表」仍列 conversations/messages——与 §2.5 已实现矛盾**

`数据库设计文档.md:128` §5 预留表列 `conversations / messages | 对话历史 | R105`，但该表已在 §2.5（行 77-96）实现并标注"0.1.5 新增，schema v2"。预留表与已实现表重复，逻辑矛盾。

> 修复：§5 预留表删除 conversations/messages 行（保留 users/roles/permissions、audit_log、vector_store 元信息表等真正未实现的）。

**L3. 需求变更记录详情只到 CH-018，CH-019~CH-025 仅总表无详情段落**
`需求变更记录.md` §二变更详情最后一条是 CH-018（0.1.7），CH-019~CH-025（0.1.8~0.1.11，含 PDF 解析知识积累、Asperger 样本分析、前端重构、R117、PDF 预览、智能体日志、扫描件修复）仅在 §一总表有行，无 §二详情段落。登记规则要求"先登记本表→再出方案→实施→标记状态"，详情缺失影响可追溯性。

**L4. 根目录 `sample/` 目录未在 AGENTS.md 目录树登记**
实际存在 `sample/`（含两个 PDF 测试样本：扫描件、Asperger 论文），AGENTS.md「目录与文件策略」目录树未列 sample/。文档与实际不一致。建议在目录树补 `sample/  # 测试样本 PDF（扫描件/论文 OCR 样本）` 或将样本移入 `scripts/`。

**L5. `agent_log` 日志文件名时间戳无微秒，同秒重启会覆盖**
`agent_log.py:26` `%Y%m%d-%H%M%S`（无 `%f`），而 `main.py:53` lantai 日志用 `%Y%m%d-%H%M%S-%f`（有微秒）。同秒内重启两次，agent 日志文件名冲突、后者覆盖前者。单机演示极低概率，定低危。

**L6. 前端 onclick 内联 + `esc` 不转义引号（N-L11 延后项，沿用）**
`app.js:160/293/603` 仍以 `esc(...).replace(/'/g,"\\'")` 构造内联 JS，安全性依赖后端 `sanitize_filename` 已去除引号类字符。建议后续改 `data-*` + 事件监听做纵深防御。

**L7. `chat_stream` 同步生成器占用线程池 worker 整条流时长（N-L12 延后项，沿用）**
`chat.py` chat_stream 为 `def` 端点 + 同步 gen + `httpx.Client.stream`，整条流（可达 120s）占一个 worker。uvicorn 默认 40 worker，单用户演示无碍。

**L8. 技术对接方案 §9.2 安全描述需复核**
N-M3 已修复"uuid 重命名"（grep 确认无 uuid 字样），但建议复核 §9.2 上传安全整段描述是否与现网实现（per-doc_id 目录 + 文件名净化）完全一致。

## 四、优点

1. **0.1.6 整改彻底可验证**：N-M1/N-M3/N-L1~N-L10 每项都能在代码中找到明确证据，注释标注修复编号（如 `chat.py` "N-M1 修复"、`store.py:118` "N-L10"），便于追溯。
2. **PDF 解析能力显著增强**：0.1.8 几何排序（pdfminer layout + 页眉页脚过滤 + 页码碎片剔除 + 双栏检测）+ 页级密度判定（混合 PDF 自动 OCR）+ 页内图片描述，覆盖了文字 PDF 的主要阅读顺序问题；边界（扫描件 OCR 版）在知识积累文档中诚实记录。
3. **智能体日志设计专业**：独立 logger 不污染应用日志、JSON 行便于解析、思维链/用量/耗时/上下文全覆盖、图片 base64 不入日志（安全）、流式与非流式统一埋点。
4. **前端重构体验提升**：左右两栏（会话历史常驻 + 消息流 + 底部输入框）贴合现代问答 UI；会话标题自动生成 + 重命名 + 删除图标 + 标题截断悬停，多会话管理完整。
5. **自动保存实现稳健**：串行化防竞争、轻提示、保留手动兜底，兼顾即时生效与可控性。
6. **变更管理持续规范**：需求变更记录 CH-001~CH-025 + 版本记录 0.1.1~0.1.11 双文档，先登记后实施；研究/知识积累类（CH-017/019/020）明确"只研究不实施"，范围控制严格。
