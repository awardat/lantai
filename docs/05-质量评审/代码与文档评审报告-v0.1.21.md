### 4.2 shell 工程问题清单

#### 🔴 高危

**H1. `server.rs:472-473` — 终端输出截断按字节切片，中文多字节字符边界必 panic**

```rust
recent.push_str(&text);
if recent.len() > 8192 {
    recent = recent[recent.len() - 4096..].to_string();  // 切片点未必是字符边界
}
```

`recent` 是 UTF-8 String，`recent.len() - 4096` 可能落在多字节字符中间。兰台服务启动输出含中文（uvicorn/app 日志，汉字 3 字节），一旦总输出超 8KB，切片点大概率不在字符边界 → **panic**。读线程是"终端输出→前端+失败特征扫描"的唯一通道，panic 后终端输出转发、`terminal:exit`、失败快速探测全部失效；ConPTY 管道无人读取，缓冲写满后 cmd 可能阻塞。

> 同类数据在 `truncate_term_buffer`（server.rs:49）已用 `floor_char_boundary` 正确处理，唯独此处漏了。**主审已逐行复核确认真实**。
> 修复：改用 `recent.floor_char_boundary(recent.len() - 4096)`，补多字节跨 8192 边界单测。

**H2. `server.rs:692-731` — keep-alive 后台服务启动竞态：前台服务仍占端口时 detached 进程必撞 EADDRINUSE**

`keep_alive_on_exit=true` 且用户选"保持运行"时，`handle_close` 直接在**前台服务仍运行**（JobObject 内 cmd+uvicorn 仍持有 8000）状态下 spawn detached 进程。detached 立即尝试绑定 8000 → EADDRINUSE 退出（错误只进日志）；随后客户端 `app.exit(0)`（lib.rs:134）才关闭 JobObject 杀掉前台树。detached 已死，端口虽释放却无人接盘。

> **"退出后保持服务运行"在常规场景（运行中直接关窗）必失败**，用户下次启动仍需冷启动。**主审已逐行复核确认真实**。
> 修复：先终止前台会话进程树（term.kill + 释放 JobObject）并等待端口释放，再启动 detached；或在 detached 包装命令里加重试循环。

## 六、优点

1. **主代码解析队列稳健**：FIFO + 动态并发 + None 哲兵优雅退出 + 重启恢复，gen 防竞态；前端轮询同步覆盖 queued。
2. **shell 状态机并发模型成熟**：探针/保活/读线程"锁内同读 stop+gen"规避 TOCTOU，重启竞态双保险——同类壳工程属上乘。
3. **进程树清理双保险**：JobObject KILL_ON_JOB_CLOSE + kill_by_port 兜底，kill_by_port 对"找不到 PID 但端口已释放"视为成功。
4. **shell 单测质量高**：netstat PID 解析（含 IPv6/乱码不误命中）、reg 代理、Content-Disposition、设置往返、缓冲截断均有测试，防回归基石。
5. **shell 安全边界意识**：on_navigation 白名单、跨源 iframe 拿不到 `__TAURI_INTERNALS__`、前端全 textContent 无注入、unsafe 均附安全注释。
6. **custom-protocol 修复有文档性注释**：Cargo.toml 注释详细说明根因，便于后人理解。
7. **变更管理持续规范**：CH-034~CH-041 + 版本记录双文档；CH-041 发布单轨决策已登记。
8. **自测规范持续生效**：主代码 0.1.18~0.1.21 无代码 bug 印证规范有效。
