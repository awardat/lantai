## 三、本次新发现问题

### 🔴 严重 / 🟠 高危

**无。**

### 🟡 中危（2 项）

**M1. clear_chunks 的 FTS 清理因删除顺序颠倒而永远为空操作——重解析场景 chunks_fts 无限累积陈旧行**
`backend/app/store.py` clear_chunks：先 `DELETE FROM chunks WHERE document_id=?`，再 `DELETE FROM chunks_fts WHERE rowid IN (SELECT id FROM chunks WHERE document_id=?)`——子查询执行时目标行已删光，IN 恒为空集，FTS 清理从不生效。与 delete_document 正确顺序（先清 FTS 后清主表）恰好相反，恰证意图是清理而实现颠倒。后果链条：失败重试/类型改判（0.1.34/0.1.36 特性）与崩溃恢复重解析（requeue_pending）都会走 clear_chunks → 每次 N 片文档重解析即遗留 N 条孤儿 FTS 行（rowid 指向已删 chunk）。用户可见检索结果暂不受影响纯属侥幸——keyword_search 的 `JOIN chunks c ON c.id = f.rowid` 把死行过滤掉了；代价是索引单调膨胀（MATCH 扫描面扩大、磁盘占用）、长期运行偏离设计语义。建议：交换两条 DELETE 顺序即可（一行级修复），另补一条回归断言「retry 后 SELECT COUNT(*) FROM chunks_fts 与 chunks 一致」防复发。

**M2. 混合检索打破对外 score 语义契约：BM25 命中返回负值、rerank 开启时替换为第三种分数量纲——API说明文档明文承诺「余弦相似度 0~1」已被违背**
三条硬证据：① store.keyword_search 定义 `score = -bm25(chunks_fts)`（负值、无量纲、"越接近 0 越相关"），而 RRF 融合返回的是**原始 dict 直接透传**（rrf 分仅内部参与排序，不回写 s["score"]）→ 同一结果列表内混排两种量纲：向量命中显示 `相似度 0.81`、关键词命中显示 `相似度 -7.53`（前端来源小字、/api/search、SSE sources 均如此渲染）；② API说明文档 :226 白纸黑字「`score` 为**余弦相似度**（0~1，4 位小数）」、Dify 章节 :125「score_threshold: float(0~1，命中过滤)」——threshold 在 BM25 命中上（负值全域 ≥ threshold? 或 ≤? 视符号而定）语义失真，外部集成方拿到 -bm25 无法解读；③ rerank 开启时 score 第三次替换为交叉编码器相关性分（0~1 另一套度量）。排序本身正确（RRF/rerank 各司其职），错在暴露层未做归一。建议方案（择一）：A. 融合/rerank 后将展示分统一映射回 0~1（如 min-max 归一或保留原路分乘路径标识入 metadata）；B. sources 增加 `score_type` 字段并在 API 文档如实记载三种量纲——两者都需同步修订 :226/:125 条款与前端来源小字表述。

### 🟢 低危（4 项）

**L1. 向量召回 `except Exception` 过宽——「维度不一致」的自愈指引也被静默吞掉**
st.search 在 embedding 模型更换后抛出的维度一致性 RuntimeError（含「请删除旧文档后重新上传…」操作指引，store.py L9 修复引入）如今同样落入降级分支，只留 log.warning：界面侧从「明确的中文修复指引 502」变为「无声的关键词结果」。降级设计的本意是网络/服务类瞬态故障，建议把维度不一致从降级路径排除（单独 except 类型再抛出），保留用户自救通道。

**L2. add_chunks 由 executemany 改单条循环（只为取 lastrowid）——批量入库吞吐小幅回退**
每片一次独立 INSERT 语句 + 一次 FTS INSERT；演示规模（几百切片）无感知，属登记备查的性能微降。可选优化：FTS 表改为 AFTER INSERT 触发器自动同步，可还原 executemany 并天然杜绝 M1 类顺序缺陷（触发器内无法引用已删除行，清理路径亦受益）。

**L3.（文档）API说明文档本轮零更新——V1.36 停留在余弦-only 世界观**
除 M2 所述 score 条款外，三项新行为均未记载：混合检索默认开启且影响所有检索端点、embedding 故障从 502 变为 BM25 降级（:128 外部检索错误码表与 :50/:228 通用 502 行需补注降级例外）、设置接口新增 enabled 字段与 rerank 槽位。与 CH-062「文档同步前置」流程要求存在差距（技术对接方案/测试方案/README 均已同步，唯独面向外部集成方的 API 契约缺席）。发版前应升 V1.37 补齐。

**L4.（文档·时序）版本记录发布表再次预写未构建目录**
`release/lantai-shell-0.1.39-windows-x64/` 已标「**当前版本**」而磁盘最新仍是 0.1.38（与上轮 0.1.38 报告 D1 同一模式）。构建后自然自洽；连续两版重复出现，建议改由 build_release.ps1 构建成功后回填该行状态标记，消手工先行的时序倒挂。

### ℹ️ 提示（非问题）

- **rerank 配置组的闲置输入项**：卡片渲染了 prompt 与 temperature 输入，但 `llm.rerank()` 不消费这两项（协议无此参数）——不误导配置判断则无需处理；供应商能力提示已对 rerank 组特判跳过（capNote），处理得当。
- **enabled 冗余落盘**：collectAiItem 对全部 8 个槽位发送 enabled=false，put_ai 对非 rerank 槽位也会写入该键——无害冗余，知悉即可。
- **FTS 查询语法注入面**：用户查询经 _fts_ngram 后若含 FTS 操作符（AND/OR/引号）会 MATCH 报错，已被 OperationalError 兜底为空列表——建议未来测试样例补一条「查询含双引号」。
- **schema v3 单次升级包含 fresh/v2 两态**：条件 `version < 3` 统一执行建表+回填，DELETE FROM chunks_fts 保证幂等重入安全。
- **空知识库首查**：chunks_fts 为空 → keyword_search 返回 []，rrf 退化正常，无游标异常。
- **requirements 注释头已随版刷新至 v0.1.39**（对照 CH-061：不作为评审项，仅记录同步义务履行情况）。

## 四、优点

1. **组合点兑现干净利落**：R106/R107 当年埋在 retriever.py 的档位 3 扩展位如期开工，`retrieve()` 对外签名纹丝不动，五个调用方（chat/stream/search/external/前端）零改动享受增强——抽象价值实打实兑现。
2. **FTS5 + 中文 bigram 选型务实**：拒绝引入 jieba/ElasticSearch 级重依赖，用 17 行正则函数解决 unicode61 中文分词短板；bigram 奇偶边界、全角标点分段、英文原样保留等细节均正确。
3. **容错纵深一致贯彻**：embedding 断线 → BM25 兜底、rerank 断线 → 混合结果直出、MATCH 语法异常 → 空列表——三层失败都不阻塞问答主链路，且每层有 log.warning 可观测（配合 TC-137~139 断言形成自测闭环）。
4. **设置页扩展遵循既定泛化路径**：rerank 作为第 8 个槽位复用 AI_KEYS/card/自动保存/testAi 全套机制，前端净增约 20 行即完成，架构泛化能力经受住检验。
