## 三、本次新发现问题

### 🟠 高危 / 🔴 严重

**无。**

### 🟡 中危（1 项）

**M1. 技术对接方案三处仍把 CH-070 已落地的整页渲染描述为「评估/备选、不引入重依赖」，与实现自相矛盾**

- **① :153 注释直相矛盾**：「PDF 页面渲染为图片：首版使用 pypdf 提取页内图片资源……整页渲染（pymupdf 等）**列入 R110 评估，不引入重依赖**。」——但 0.1.38 已引入 `pymupdf>=1.28`（requirements.txt:19，注释标注用途）并在 `_ocr_pdf` 作为标准兜底通道调用。「说不引入实际已引入」，新维护者必然困惑。
- **② :335 口径过期**：风险对策表中「扫描 PDF 页面图片提取瓶颈：pypdf 提取页面图片（R110 备选：整页渲染…）」——整页渲染已从「备选」变为「无位图 PDF 的既定兜底路径」，表述应升级为落地状态。
- **③ §4.3 分类表缺行**：矢量/无位图 PDF 整页渲染兜底（CH-070）、pdfminer 打开异常回退 pypdf（CH-072）、OCR 文本层空格规整（CH-073）三项机制均未进分类表——上两轮同类问题（0.1.30 办公文档、0.1.37 TIFF 转码）均以此形式修复过，本轮再次漏网。

建议：:153 改为「0.1.38 起 R110 整页渲染落地：pymupdf（zoom 2 ≈144 DPI）作为无内嵌位图 PDF 的 OCR 兜底，详见 §6.1b 同期变更记录」；:335 同步改「已落地」口径；§4.3 补矢量 PDF 行（判定：pypdf 提取位图为 0 → 整页渲染 → OCR）并附 pdfminer 异常回退与 clean_ocr_spacing 说明。

### 🟢 低危（3 项）

**L1.（代码·性能）CH-072 回退分支重复构造 PdfReader：N 页 PDF 触发 N 次全文解析**
`filetype.py` pdf_text_layers 异常回退分支：先 `reader = PdfReader(str(path))` 创建实例，其后循环却调 `_pypdf_page_text(path, idx)`——该函数内部每次调用都重新 `PdfReader(str(path))` 解析整份文档的 xref/页树。N 页非标 PDF 即 N+1 次全文打开（56 页样本约 57 次），大文件有明显 CPU 浪费；且回退分支内的 `reader` 变量除隐式「验证 pypdf 能否打开」外未被使用。建议：`_pypdf_page_text` 增加 reader 参数重载（或在回退分支内联使用已构造实例），一行级重构。

**L2.（代码·资源）`pdf_render_page_images` 将全部页面 PNG 一次性载入内存**
同函数返回前把所有页渲染结果累积进 list（zoom=2 下每页 PNG 约 1~3MB）：数百页矢量 PDF 内存峰值可达数百 MB 以上。与既有 `pdf_extract_page_images` 全量提取模式一致（历史取舍），但渲染通道对任意非空 PDF 都必然产出内容，触发面显著扩大。演示规模可接受，建议登记为档位 3 优化项：改生成器逐页产出版本，配合 `_ocr_pdf` 逐页消费。

**D1.（文档·时序）版本记录发布表先行标注了尚未构建的 0.1.38 发布目录**
版本记录.md 发布物清单已写「0.1.38（壳）｜ release/lantai-shell-0.1.38-windows-x64/ ｜ 当前版本」，但磁盘 release/ 实际最新为 0.1.37（已实证列目录）——CH-054/CH-062 流程下构建发布发生在用户确认提交之后。若本轮审核引发整改升版（如 M1），该行还需随版本号调整。与既往「等价变更合入同一发布批次」（0.1.33/0.1.34 并入 0.1.35 批次）的做法相比，属于先承诺后兑现的时序写法：构建完成后即自洽，但在等待确认窗口内文档与磁盘事实不符。注：此项是文档对物理产物状态的先行声明，非纯版本号比对问题，故不适用 CH-061 豁免。

### ℹ️ 提示（非问题）

- **external.py 协议容错取向**（知悉即可）：`int(rs.get("top_k") or 5)` 使显式 top_k=0 静默回落默认值 5 而非 400；score_threshold 为负恒通过、大于 1 则全过滤，均按宽容语义放行——Dify 正常客户端不会触发。
- **clean_ocr_spacing 的语义边界**：中文法律/公文标题惯用字间空格（如「总 则」「第一章 总 则」）会被归一为「总则」——对检索/切块通常是期望行为，但意味着文本不再逐字节忠实原文；如未来需要保真展示可用原始文本另行存档。
- **CJK 扩展 B~F 区汉字**（U+20000 起）不在正则覆盖域：生僻古籍用字场景可再扩，现网中文公文/论文极少涉及。
- **打包体积 +约 20MB**（pymupdf）：CH-070 已登记待构建确认，发行物校验脚本现有断言（data/logs/settings.json）不含体积项，无需动作。
- **文档同步质量良好**：API说明文档 V1.36 §2.4c 含字段表/请求响应双示例/401·400·502 错误码且与实现逐项吻合；测试方案 V1.7 TC-133~136 与四项功能一一对应（含 GBT 回归断言）；CH-069~073 六条登记详实可追溯；技术对接方案 §6.1b 补齐端点。

## 四、优点

1. **Dify 适配改动最小化设计成熟**：完全复用 token 管理、retriever 与既有过rror 处理约定，裸协议响应不走内部信封且三处文档如实标注「暂不细分/暂不处理」的功能边界，诚实清晰。
2. **三层降级链设计严密**：内嵌位图 → 整页渲染 → 明确中文报错，每层职责单一；GBT TIFF（有位图）与商用密码条例（纯矢量）两条真实样本路径互不干扰，回归安全。
3. **clean_ocr_spacing 实现质量高**：不动点循环处理连锁暴露空隙、正则域精确排除假名、三处文本产出接入保证预览/入库零残留——一个 12 行函数解决了一类真实客户样本问题。
4. **CH-062 文档同步前置流程持续生效**：本轮六处文档在交付前已全部就绪，仅剩技术对接方案的落地状态描述滞后（M1），颗粒度明显小于往轮。
