## 一、PDF 为什么"编辑/解析不友好"（原理层面）

PDF 是**页面描述模型（显示导向）**，不是文档结构模型——这是所有解析难题的总根源：

| 原理特性 | 具体表现 | 对解析的影响 |
|----------|----------|--------------|
| **内容是"画"出来的** | 文本通过 `Tj/TJ`（show 操作）绘制，图形是路径，图像是 XObject；没有"段落/标题/表格"概念 | 无结构可循，需自行重建 |
| **绘制顺序 ≠ 阅读顺序** | 内容流中对象顺序 = 视觉层叠顺序；双栏、页眉页脚、脚注、浮动图注可按任意顺序绘制 | 直接按流顺序提取会得到乱序文本 |
| **文本可能被切碎** | 单词被拆成多个 show 操作（字距调整/kerning）；字符可能逐字绘制 | 需要按位置合并字符 |
| **编码映射可能缺失/错误** | 字符码 → Unicode 靠 ToUnicode CMap；缺失时只有 CID，Type3 字体无统一编码 | 提取出乱码或空文本 |
| **坐标系统** | 内容流用矩阵变换（`cm`），文本定位用 `Tm/Td`；位置是绝对坐标 | 必须重建 2D 布局才能推断语义 |
| **表格只是视觉组合** | 表格 = 线条（图形路径）+ 文本的视觉对齐；无边界表格连线条都没有 | 表格识别本质是"版面猜测" |
| **图表无语义** | 位图 XObject（截图/扫描）、矢量路径（matplotlib 输出）均无数据语义 | 图表内容需视觉模型/OCR 二次理解 |

> 一句话：PDF 只保证"看起来对"，不保证"读起来有结构"。解析质量的上限由生成端决定（LaTeX/Word 导出的文本层通常良好，扫描件为 0）。

## 二、如何确保 PDF 被正确解析（策略分层）

### 2.1 分层路由（按 PDF 类型）

| 类型 | 判定 | 解析通道 |
|------|------|----------|
| 文本型 | 有可用 ToUnicode，提取文本可读 | 文本提取 + 布局后处理（本主题 §3/§4） |
| 扫描件 | 无文本层/乱码 | OCR（兰台 pdf_image 通道：视觉模型） |
| 混合型 | 部分页有文本、部分页为图 | **按页判定**：逐页统计文本密度，页级路由 |

> 兰台现状：整文档按"文本层总字符数 < 阈值"降级 OCR——**增强点：改为页级判定**（文档内常见"前几页扫描 + 后文文本"）。

### 2.2 解析质量校验（正确性度量）

| 检查项 | 方法 | 失败处置 |
|--------|------|----------|
| 可读性 | 提取文本中不可打印字符/替换符（U+FFFD）比例 | 该页转 OCR |
| 覆盖率 | 每页提取字符数 vs 页面面积估算；空页检测 | 空页转 OCR |
| 连续性 | 相邻文本块间距异常（断层） | 标记人工复核/转 OCR |
| 乱码检测 | 常见乱码模式（如莫诺字体映射错误） | 转 OCR |

> 原则：**"提取成功"≠"提取正确"**；文本通道与 OCR 通道互为兜底，宁可降级不可静默出错。

## 三、跨页表格的结构完整性

### 3.1 问题本质

PDF 无"表格"对象；跨页表格被物理切分：
- 表头在每页重复（或只在首页出现）；
- 行可能在页尾被截断、续行在下一页；
- 页边距处视觉断裂。

### 3.2 对策（由浅入深）

| 方案 | 做法 | 适用 | 代价 |
|------|------|------|------|
| A. 规则检测+拼接 | 按文本行 x 坐标对齐聚类识别表格列；跨页时以"表头行模式"（如 `====` 线条或首行单元格样式）匹配续表；**重复表头去重**，页尾断行按行号/坐标连续性拼接 | 有清晰边界的表格 | 实现中等，无边界表格失效 |
| B. 专用表格提取库 | pdfplumber `extract_table`（按线条+文本）、camelot（lattice/stream 两种模式） | 有线表格/简单排版 | 对复杂合并单元格仍弱 |
| C. 视觉表格识别 | 页面渲染为图片 → 表格结构模型（如 PaddleOCR 表格、Table Transformer）输出 HTML table | 复杂/无线表格、扫描件 | 依赖重（与"避免重依赖"约束冲突，宜独立服务） |
| D. LLM 视觉表格理解 | 直接让视觉模型按图片输出 Markdown 表格 | 任意表格 | 质量不稳定，需校验 |

**跨页合并流程**（推荐 A 起步）：
```
页级表格检测 → 识别"表头重复页"（表头行与上页相同 → 丢弃本页表头）
→ 按列结构匹配续表 → 合并单元格内容 → 输出单一结构化表（Markdown/行列数组）
→ 行级坐标记录保留（供溯源）
```

> 兰台现状：docx 走 python-docx 表格提取；**PDF 表格未专门处理**（文本流中表格内容被顺序打散）。R117 建议：先做方案 A（页级表格检测 + 表头去重 + 续行拼接），返回 Markdown 表格切片。

## 四、还原真实阅读顺序

### 4.1 问题本质

内容流顺序 ≠ 阅读顺序。典型破坏因素：双栏版面（论文）、页眉页脚、脚注、图注、边栏、装饰性文本。

### 4.2 对策：几何布局重建（规则引擎）

```
① 提取词级/块级元素（文本 + 坐标 + 字号）——pdfminer.six 的 layout 模式天然按位置输出
② 过滤页眉页脚：页边距区域（上 5%/下 5%）+ 跨页重复内容模式（同一文本每页出现 → 页眉）
③ 栏检测：对正文块按 x 坐标聚类——单峰=单栏；双峰=双栏（先左栏后右栏，各自内部 y 排序）
④ 块内排序：主排序 y（上→下），次排序 x（左→右）
⑤ 段落合并：按行高/行距聚类为段落，避免把标题与正文揉在一起
⑥ 特殊元素归位：脚注（页底小字号）与图注（紧邻图像）可插回正文流或独立成段
```

### 4.3 模型路线（远期）

版面分析 + 阅读顺序模型（LayoutLM / DocLayout-YOLO / 多模态版面模型）直接输出 reading order；但依赖重，宜独立服务（同 OCR 引擎评估，R110）。

> 兰台现状：pypdf `extract_text()` 按内容流顺序输出，**双栏/页眉页脚会乱序**。R117 建议：改用 pdfminer.six（pdfplumber 底层，纯 Python、无重依赖）的 layout 模式 + 上述规则引擎，演示级文档（单栏为主）即可显著改善切片质量。

## 五、图表信息与页面关系绑定

### 5.1 问题本质

- 图表是图像/矢量路径，无文本语义；
- "图 3 所示"的引用关系在正文，图表本体可能在另一页；
- 图题（caption）是唯一锚点，但识别需模式匹配。

### 5.2 对策

| 环节 | 做法 |
|------|------|
| 图表抽取 | 位图：`page.images` 抽取（兰台已用于 pdf_image）；矢量图（chart 是路径）：区域渲染为图片（pymupdf/poppler，重依赖→独立服务）或整页图走视觉通道 |
| 图题识别 | 模式匹配：`图 N` / `Figure N` / `表 N` / `Table N`（首行/首段位置）→ 与最近图像区域绑定（距离最近原则） |
| 引用识别 | 正文中 `图 N 所示/见图 N` 模式 → 建立"引用段落 ↔ 图 N ↔ 图题 ↔ 源页码"四元关系 |
| 语义化 | 图像 → 视觉模型生成描述（兰台 image 通道已有能力）→ 描述文本向量化入库；表格 → §3 结构化提取 |
| 页面关系绑定 | 记录：图表源页码、所在区域坐标、被引用段落；RAG 命中图表描述切片时，溯源可跳转源文件对应页 |
| 数据绑定（远期） | 矢量图表取数（ChartQA 类模型）或 OCR 图表内数字 |

### 5.3 对兰台的落地建议

- 文字 PDF 解析时**检测并抽取页内图像区域** → 走视觉模型描述（复用 image 通道配置）；
- 图题/引用用正则绑定，图描述切片与正文切片通过"图号"关联；
- 检索命中图表描述时，来源卡片标注"图 N（第 M 页）"，预览定位到该页。

## 六、结论与路线建议（对兰台）

| 优先级 | 事项 | 依赖 |
|--------|------|------|
| 近期（演示级，纯 Python 可做） | ① pypdf → pdfminer.six layout 模式 + 几何排序 + 页眉页脚过滤（双栏检测可选）② 页级文本密度判定（混合 PDF 页级路由）③ 文字 PDF 页内图片抽取 + 视觉描述 + 图题/引用绑定 ④ 跨页表格：表头去重 + 续行拼接（规则版） | 无新依赖（pdfminer 为 pdfplumber 底层，纯 Python） |
| 中期 | pdfplumber 表格提取（extract_table）接入；表格结构质量校验 | pdfplumber（纯 Python） |
| 远期 | 版面分析/阅读顺序模型、表格视觉模型、图表取数；pymupdf 渲染 —— **依赖较重，宜独立服务/容器**（同 R110 OCR 引擎评估） | 与"避免 torch/onnxruntime 重依赖"约束冲突，需独立组件 |

> 关键认知：**解析质量天花板由生成端决定**；对不可靠的文本层，正确姿势是"分层路由 + 双向校验 + 可降级"，而不是追求单一解析器全解。
