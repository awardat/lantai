# 模型能力探测研究：模型清单能否携带能力信息

| 项目 | 内容 |
|------|------|
| 研究类型 | 专项调研（**只研究，不实施，不加入版本**） |
| 研究时间 | 2026-08-23 |
| 发起人 | 用户（"获取模型清单的时候是否可获取模型的能力，比如对话、视觉等；以预置的提供商范围，单独研究"） |
| 关联功能 | 设置页「测试」：`POST /api/settings/ai/test` → `GET {base}/models` 获取模型清单 |
| 结论摘要 | OpenAI 兼容 `/v1/models` 标准**不携带能力字段**，仅 Ollama 原生 `/api/tags` 提供 `capabilities`（completion/embedding）；视觉能力无标准探测途径。建议以"预置目录人工声明 + 模型名模式匹配"为增强方向，待用户决策 |

---

## 一、研究背景

设置页「测试」功能当前仅返回模型 **ID 清单**（`GET {base}/models` → `data[].id`），前端展示为可点击的模型标签。用户提出：能否同时获取每个模型的**能力**（对话 chat / 视觉 vision / 向量化 embedding），以便自动判断"该模型能否用于图片理解 / OCR / embedding 槽位"，而不依赖人工预置。

## 二、现状（兰台实现）

| 环节 | 实现 |
|------|------|
| 测试连接 | `llm.list_models()` → `GET {base}/v1/models`，返回 `data[].id` 列表 |
| 能力来源 | 预置供应商目录（`vendors.py`）人工声明：`capabilities: [chat/vision/embedding]` + 各能力推荐模型 |
| 能力提示 | 前端按"槽位能力 vs 供应商能力"比对，不匹配时提示（如 embedding 槽位选 DeepSeek） |

即：目前能力信息**只来自人工预置**，不来自运行时探测。

## 三、预置供应商模型清单接口调研

| 供应商 | 接口 | 返回结构 | 是否含能力字段 |
|--------|------|----------|:---:|
| **Ollama（本地）** | 原生 `GET /api/tags` | `{models:[{name, capabilities:["completion","embedding"], ...}]}` | ✅ **有**（[Ollama API 文档](https://github.com/ollama/ollama/blob/main/docs/api.md)、[capabilities 字段 Issue](https://github.com/ollama/ollama/issues/14964)）；但**不区分视觉**，`completion` 同时覆盖文本与视觉模型 |
| Ollama 兼容端点 | `GET /v1/models` | `{data:[{id, object, created, owned_by}]}` | ❌ 标准 OpenAI 兼容结构，无能力 |
| **DeepSeek** | `GET /v1/models` | `{data:[{id, object, created, owned_by}]}` | ❌ 标准结构（[Consiliency 模型发现验证](https://github.com/Consiliency/treesitter-chunker/blob/main/.ai-dev-kit/skills/model-discovery/cookbook/openai-models.md)） |
| **OpenCode Go 代理** | `GET /v1/models` | 转发上游，标准结构 | ❌ 仅 ID |
| **通义 DashScope** | `GET /v1/models`（兼容模式） | `{data:[{id, object, created, owned_by}]}`；原生另有[模型列表接口](https://help.aliyun.com/zh/model-studio/list-models)（返回模型元信息，能力需按模型名/文档判断） | ❌ 兼容端点无；原生接口无结构化能力字段 |
| **智谱 GLM** | `GET /v1/models` | 标准 OpenAI 兼容（社区实现按 id/object/owned_by 解析，如 [ragflow 的 ListModels](https://github.com/infiniflow/ragflow/pull/14886)） | ❌ |
| **Kimi（Moonshot）** | `GET /v1/models` | 标准结构（[Kimi 平台文档 list-models](https://platform.kimi.com/docs/api/list-models.md)） | ❌ |
| **硅基流动** | `GET /v1/models` | 标准结构（[SiliconFlow 文档-获取模型列表](https://docs.siliconflow.cn/cn/api-reference/models/get-model-list)） | ❌ |
| **OpenAI** | `GET /v1/models` | `{data:[{id, object, created, owned_by}]}` | ❌ 标准结构（能力见官方模型文档，接口不返回） |

## 四、结论

1. **OpenAI 兼容协议标准中，模型清单接口不携带能力信息**——预置 8 个供应商中 7 个（含全部云端厂商）的 `/v1/models` 均为 `id/object/created/owned_by` 标准结构；仅能拿到模型 ID。
2. **唯一例外是 Ollama 原生 `/api/tags`**：返回 `capabilities: ["completion", "embedding"]`，可区分"文本/视觉（合称 completion）"与"embedding"，但**无法区分视觉能力**（视觉模型也标 completion）。
3. 视觉（vision）能力**无标准运行时探测途径**：OpenAI 兼容体系未定义该元数据；Ollama 需解析模型 template/项目文件（`/api/show`）才可间接推断，不稳定。
4. 因此：**运行时"自动发现能力"不可行（除 Ollama 的 completion/embedding 二分类外）**，能力信息只能来自人工维护（兰台 `vendors.py` 预置目录的做法是合理的）。

## 五、可选增强方案（均未实施，待决策）

| 方案 | 内容 | 收益 | 代价/风险 |
|------|------|------|-----------|
| A. 维持现状 | 能力仅来自预置目录，测试连接只列 ID | 无 | 新模型/自定义网关的能力需人工配置 |
| B. Ollama 增强探测 | 测试连接对 `ollama` provider 额外调 `/api/tags`，用 `capabilities` 自动标注 completion/embedding | 本地模型列表自动带能力标签 | 视觉无法标注；需处理 `/api/tags` 失败回退 |
| C. 模型名模式字典 | `vendors.py` 增加"能力推断规则"：按模型名模式匹配（`*-vl*`/`llava`/`gpt-4o`→vision；`bge*`/`embedding*`→embedding；其余→chat），测试连接时对清单自动打标 | 云端清单也能显示推断能力，与人工声明互补 | 模式匹配可能误判（名称含 vl 但非视觉等）；仍需人工兜底 |
| D. 厂商文档快照 | 各厂商模型能力表（名称→能力）随预置目录维护 | 精确 | 维护成本随模型迭代上升，等同人工声明 |

**建议**：优先 **B + C 组合**（Ollama 用真实 capabilities，云端用命名模式推断 + 预置目录兜底），作为后续迭代候选；本版不实施。
