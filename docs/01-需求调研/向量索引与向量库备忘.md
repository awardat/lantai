## 一、背景：为什么需要索引

兰台当前检索 = **numpy 全表余弦**（暴力扫描）：正确但复杂度 O(N×D)，N 超十万级开始吃紧。
**ANN（近似最近邻）索引**以"极小的召回损失"换取"指数级提速"：

| 方式 | 复杂度 | 十万级向量单次检索 |
|------|--------|--------------------|
| 暴力扫描 | O(N×D) | ~百 ms~秒级 |
| ANN（HNSW 等） | O(log N) | ~亚毫秒~几 ms |

**HNSW（Hierarchical Navigable Small World）**是当前事实标准，pgvector/Qdrant/FAISS 均内置。

### HNSW 原理（通俗版）
- **多层图**：底层包含全部向量（邻居=相似点），上层逐层稀疏（每层是下一层的"高速公路"）
- **搜索**：从顶层粗粒度"跳"到目标区域，逐层下钻，底层精细查找（类似跳表）
- **贪心导航**：每层从入口点沿"最相似邻居"移动，直到局部最优
- **参数**：`M`（每点邻居数，越大召回越高/内存越大）、`efConstruction`（构建精度）、`efSearch`（搜索宽度，越大召回越高/越慢）
- 特性：**无需训练**（增量插入）、召回率高、支持删除（墓碑标记）

## 二、三方案对比总表

| 维度 | **pgvector** | **Qdrant** | **FAISS** |
|------|--------------|------------|-----------|
| 形态 | PostgreSQL 扩展（表内列） | 独立向量数据库服务（Rust） | 应用内 C++/Python 库（非服务） |
| 索引 | IVFFlat / **HNSW** | HNSW（默认）+ 量化 | Flat / IVF / **HNSW** / IVF-PQ 等十余种 |
| 混合检索 | 需配合 PG FTS（tsvector） | **内置稀疏向量 BM25**（R107 契合） | 无（需自建 BM25 融合） |
| 过滤 | SQL WHERE 天然支持（索引内过滤） | **payload 过滤**（索引感知） | 后过滤为主（过滤后重排） |
| 持久化/备份 | PG 体系（WAL/备份/主从） | 快照/集合备份；集群模式 | **无**（内存/文件需自管） |
| 部署 | 随 PG | 单机二进制 / Docker / 集群 | 嵌入进程（可自行封装服务） |
| 生态 | SQL/ORM/BI 全通 | REST/gRPC SDK 齐全 | Python/C++/GPU |
| 距离 | L2 / IP / **Cosine** | L2 / IP / Cosine / Manhattan | L2 / IP / Cosine 等 |
| 维度上限 | HNSW ≤ **2000** 维 | 默认 65536 | 无硬限 |
| 适合 | 已有 PG、<千万级、要 SQL 一体化 | 独立向量服务、混合检索、中大规模 | 最大规模/性能、GPU、深度定制 |

## 三、pgvector（PostgreSQL 扩展）

- **软件**：`pgvector` 扩展（开源，PostgreSQL 12+，官方维护）；通过 `CREATE EXTENSION vector`
- **原理**：`vector` 类型列 + **HNSW**（v0.5+）或 IVFFlat 索引；索引内感知 `ORDER BY embedding <=> $1 LIMIT k`
- **特性**：与业务表同库 JOIN/事务/权限/备份；支持过滤（`WHERE doc_id=...` 与向量检索同一索引路径）；余弦用 `<=>` 距离算子；半精度向量（`halfvec`）省一半内存
- **环境要求**：PG 12+（推荐 15+）；HNSW 索引内存随向量量增长（向量加载 + 图）；`maintenance_work_mem` 影响建索引；无 GPU
- **注意**：HNSW 维度 ≤2000（bge-m3 1024 维 OK）；IVFFlat 需先建表后建索引（lists 参数按数据量调）
- **兰台接入**：`store.py` 换实现：SQLAlchemy + `INSERT ... RETURNING` 批量写、`ORDER BY embedding <=> %s LIMIT k` 检索，业务代码不变（R108）

## 四、Qdrant（独立向量数据库）

- **软件**：Qdrant（Rust，开源）；单机二进制或 Docker；分布式集群（多节点 + 分片）
- **原理**：HNSW 默认索引；**payload 过滤在索引内执行**（过滤+近邻一体，避免"先检索后过滤"漏召回）；支持**标量/乘积量化**（省内存换精度）
- **特性**：**稀疏向量（BM25 权重）与稠密向量混合检索**（R107 hybrid 直接落地）；REST/gRPC；集合（collection）级配置（向量维度/距离/量化）；快照备份/恢复；多租户 payload 分区
- **环境要求**：单机内存建议 ≥ 向量总量 2~3 倍（HNSW 图开销）或启用 **mmap 磁盘模式**（on-disk）；Docker 一键；Linux/Windows/macOS；无 GPU 需求（CPU 高性能）
- **注意**：业务元数据（文档/用户/会话）仍需关系库或双写 payload；运维多一套服务
- **兰台接入**：`store.py` 换实现：`PUT /collections/{doc_id}/points`（payload 带 doc_id/category）、`POST /collections/points/search`（with_payload + filter），业务代码不变

---

## 五、FAISS（应用内索引库）

- **软件**：Meta FAISS（C++/Python，`faiss-cpu` / `faiss-gpu` pip 包）
- **原理**：**IVF**（倒排文件：聚类分桶，只搜邻近桶）+ **PQ**（乘积量化：向量分段压缩，大幅省内存）+ HNSW 图；GPU 版用 cuBLAS/cuDNN 加速构建与搜索
- **特性**：索引类型最全（IndexFlatIP / IndexIVFFlat / IndexHNSWFlat / IndexIVFPQ / IndexHNSWPQ…）；批量构建极快；**无内置服务/持久化/鉴权**——需自行封装（REST 服务 + 索引落盘/加载）；内存常驻（或 mmap 映射文件）
- **环境要求**：CPU 版 pip 即装（注意与 Python 版本 wheel 匹配，Python 3.14 需验证）；GPU 版需 CUDA + 显卡；索引加载到内存（百万级 × 1024 维 ≈ 4GB）
- **注意**：增删改需自行管理（HNSW 删除为标记，定期重建索引回收）；训练（IVF 聚类）需代表性子集
- **兰台接入**：封装 `VectorStore` 实现：内存索引 + 落盘（.index 文件）+ 小 HTTP 包装；或跳过（Qdrant 已覆盖此需求且自带服务化）

## 六、选型建议（兰台视角，R108 落地路径）

| 场景 | 推荐 |
|------|------|
| 已有 PostgreSQL、<1000 万向量、要 SQL 一体化 | **pgvector**（增量最小：同库事务/权限/备份） |
| 独立向量服务、要混合检索（BM25+向量）、中等规模 | **Qdrant**（R107 一步到位） |
| 应用内嵌入、最大规模/极致性能/GPU、可自研服务化 | **FAISS** |
| 演示/小型自用 | 维持 SQLite + numpy（现状） |

**迁移路径**：`store.py` 的 `VectorStore` 抽象为唯一入口 → 新增实现（pgvector 或 Qdrant 客户端）→ 配置项 `vector_store` 切换 → 全量重向量化入库（历史切片迁移脚本）→ 回归（检索结果对比暴力法 recall）。

## 七、实践要点（有益内容）

1. **归一化**：余弦距离 ↔ 内积等价的前提是向量归一化；embedding 后统一 L2 归一化，索引用 IP 更快
2. **参数调优**：HNSW `M=16~32`、`efConstruction=100~200`、`efSearch=50~200`——`efSearch` 是延迟/召回的旋钮；线上用 Recall@k 评估（暴力法作基准）
3. **过滤策略**：优先"索引内过滤"（Qdrant payload / pgvector WHERE）；"先检索后过滤"会因 k 太小漏召回（补救：检索 3~5 倍候选再过滤）
4. **混合检索**：`score = α·cos + β·bm25`（α+β=1 或加权归一）；Qdrant 稀疏向量原生支持；pgvector 配 PG FTS（tsvector + ts_rank）
5. **内存估算**：HNSW 图开销约向量的 1.2~1.5 倍 + 向量本体；量化（PQ/scalar）可省 4~16 倍内存（召回略降）
6. **更新与删除**：HNSW 删除=墓碑，长期增删需定期重建索引；pgvector HNSW 重建 `REINDEX`；Qdrant 自动处理
7. **维度与模型**：bge-m3（1024 维）适合 HNSW；超 2000 维注意 pgvector 限制；低维（<128）可考虑暴力或 IVF
8. **中文 embedding**：中文建议 bge-m3 / text-embedding-v3 系（已入兰台推荐）；检索前查询改写（同义词/纠错）可提升召回
9. **评估闭环**：建 100~1000 条标注查询集 → Recall@k 对比（暴力基准 vs ANN）→ 调 efSearch/量化 → 上线灰度对比
10. **备份与恢复**：向量库与业务库一起纳入备份策略（pgvector 随 PG WAL；Qdrant 快照；FAISS 落盘文件）
11. **可观测**：记录检索延迟/召回率/内存，纳入 Prometheus 指标（与企业级架构备忘衔接）
12. **成本**：GPU 索引（FAISS-GPU）只在高查询 QPS 时值得；CPU HNSW 通常够用

## 八、术语表

| 术语 | 含义 |
|------|------|
| ANN | 近似最近邻（牺牲少量精度换数量级提速） |
| HNSW | 分层可导航小世界图（多层图 + 贪心搜索） |
| IVF | 倒排文件（聚类分桶，只搜邻近桶） |
| PQ | 乘积量化（向量分段压缩存储） |
| Recall@k | 前 k 结果中命中真实最近邻的比例（召回率） |
| efSearch / M | HNSW 搜索宽度 / 每点邻居数 |
| 稀疏向量 | 大部分维度为 0 的向量（BM25 权重表示） |
| payload | Qdrant 中随向量存储的元数据（过滤用） |
