## 一、数据库与存储

**首选：PostgreSQL + pgvector**——企业增量成本最低（复用现有 DBA/运维/备份/权限体系），关系数据（文档元数据/用户/RBAC/对话历史）与向量同库、事务一致；HNSW/IVFFlat 索引支撑百万~千万级向量。

**备选**：

| 方案 | 适用 |
|------|------|
| **Qdrant** | 规模中等、要混合检索（内置 BM25 稀疏向量，契合 R107）且部署简单 |
| **Milvus** | 超大规模 / GPU 索引（十亿级向量） |
| **OpenSearch / ES** | 已有 ES 基础设施的企业复用（dense vector + BM25） |

**企业落地配套**：元数据过滤（文档/时间/权限）、混合检索融合、高可用备份、鉴权审计；兰台 `VectorStore` 抽象（R108）为唯一存储入口，替换 = 新实现 + 配置项，业务代码不感知。

## 六、文件存储组织方式（uploads 目录设计备忘，2026-08-24 讨论）

**讨论背景**：当前 `data/uploads/<doc_id>/<文件名>`（每个文档一个数字目录）；讨论是否改用 hash 等方式把所有文件分散到数十个目录。

### 6.1 现状方式：`uploads/<doc_id>/<文件名>`（每文档一目录）

**优点**：
1. 路径计算零成本（doc_id → 路径直接拼接，无间接层）；
2. 删除天然原子（删文档 = 整目录删除，级联清理源文件）；
3. 无文件名冲突（每文档独立目录）；
4. 调试直观（目录编号 = 数据库主键）；
5. 与数据库强一致（目录即主键索引，孤儿目录/记录一眼可见）。

**缺点**：
1. 目录数 = 文件数：NTFS 大量小目录 → MFT 开销、资源管理器/杀软/备份/zip 枚举慢（**数万文件量级才显现**）；
2. 顺序 id 泄露业务量（本地单机无碍）；
3. id 与内容解耦：无法内容寻址/去重；数据库重建后目录残留需手工清理；
4. 多实例数据合并时 id 冲突 → 目录冲突。

### 6.2 Hash 分散方案（如 `uploads/<hash前2位>/<hash后2位>/<文件>`）

**优点**：目录均匀分散（固定桶数、单目录文件数可控）；内容 hash 可去重/缓存友好；不暴露数量；与对象存储桶化模式对齐。

**缺点/代价**：
1. 路径计算多一步（内容 hash 需读全文计算，大文件多一次 IO）；
2. 可读性崩坏（路径看不出文档归属，排查多一层间接）；
3. 删除变复杂（桶内按名删单文件 + 空桶清理）；
4. 同桶同名需重命名策略；
5. 内容变更 → hash 变 → 旧文件孤儿；
6. 不提升安全性（hash 只是分布，非加密/权限）。

### 6.3 结论与建议（讨论结论，只保存不执行）

1. **演示级（几百文件）：保持现状**——所有缺点都是量级问题而非设计问题，现状的简单/原子删除/可调试恰好是单机演示最看重的；
2. **若要分散：推荐"id 取模桶化"折中**——`uploads/{doc_id % 16}/{doc_id}/{name}`（顶层 16 桶，桶内保留数字目录）：改动仅上传/删除/预览三处路径拼接 + 一个取模函数；保留全部现状优点（整目录删、按 id 调试、无冲突）；桶数 16~256 按需，取模代价为 0；
3. **不建议内容 hash**：无去重需求，读全文算 hash 纯浪费，且删除/迁移逻辑全面变复杂；
4. **架构预留**：把"doc_id → 路径"收敛为 store 层单一函数（现散落在 docs.py 三四处），未来换对象存储/多平台只改一处——小改动，可并入某次版本顺手做。

## 七、本地 AI 推理硬件方案（显卡 / CPU 搭配，2026-08-24 讨论）

**目标**：为兰台本地模型栈（问答 7B + 视觉 7B + bge-m3）规划"流畅"硬件搭配，覆盖演示、标准、企业三级。

### 7.1 性能模型与关键认知

- **生成速度公式**（decode）：`token/s ≈ 内存/显存带宽 × 利用率 ÷ 模型权重大小`
- 基准：7B Q4 量化 ≈ 4.7GB；**RTX 4070**（带宽 504 GB/s，利用率 ~75%）实测 7B Q4 约 **70~90 token/s**
- **第一认知：内存容量 ≠ 带宽**。加大内存只加容量不加速度；带宽 = **通道数 × 单通道速率**，加内存条（通道）才提速
- **压力点排序**：内存带宽（decode 主瓶颈）> 指令集（AVX-512 / AMX / BF16）> 核心数（仅并发/大 prompt 时吃重）
- 显存不够时模型层 offload 到内存 → 速度断崖式下降（显卡方案的第一铁律：显存 ≥ 模型 + 余量）

### 7.2 显卡方案（NVIDIA，推荐）

| 档次 | 显卡示例 | 显存 | 能跑什么（7B Q4 ≈ 4.7GB/个） | 流畅度 |
|------|----------|------|------------------------------|--------|
| 入门可用 | RTX 4060 / 3050 8G | 8GB | 单个 7B（问答或视觉二选一，切换加载等 10~20s） | ✅ 单模型流畅 |
| **推荐** | **RTX 3060 12G** | 12GB | 问答 7B + 视觉 7B 基本共存；或单模型上 14B Q4 | ✅ 全功能流畅，性价比首选 |
| 舒适 | RTX 4070 Ti Super / 4080 | 16GB | 双 7B 宽裕 + 长上下文；单模型可上 32B Q4 | ✅✅ |
| 顶配 | 4090 / 5090 | 24GB+ | 32B Q4 流畅；双模型无压力 | ✅✅✅ |

配套：内存 16GB 起步、**32GB 推荐**（offload 兜底）；AMD 卡 ROCm 驱动折腾不推荐演示；核显只能走 CPU 方案。

### 7.3 纯 CPU 方案（桌面 / 工作站）

| 配置 | 7B Q4 速度 | 体验与建议 |
|------|-----------|-----------|
| 双通道 DDR4（~25GB/s） | 2~3 t/s | ❌ 卡顿；仅 3B 模型可用 |
| 双通道 DDR5（~60GB/s），6~8 核 | 8~10 t/s | ⚠️ 勉强；问答降级 qwen2.5:3b 速度翻倍 |
| 4 通道工作站（Xeon W） | 17~20 t/s | ✅ 演示可接受 |
| 内存 | 32GB 推荐 | 权重 5GB + 系统 + WebView 均吃内存 |
| 视觉/OCR | — | **纯 CPU 不建议**（7B VL 每图几十秒~几分钟） |
| bge-m3 embedding | 无压力 | 仅入库时批处理一次，慢无感 |

### 7.4 服务器 CPU 方案（Xeon / EPYC，企业现网）

| 平台 | 通道/带宽 | 7B Q4 估算 | vs 4070 |
|------|-----------|-----------|---------|
| EPYC 7003（Milan，DDR4-3200） | 8ch / ~204GB/s | 24~28 t/s | ~35% |
| Xeon 4/5 代（DDR5-5600 + AMX） | 8ch / ~358GB/s | 45~50 t/s | ~60% |
| **EPYC 9004/9005（DDR5-6400）** | **12ch / ~614GB/s** | **75~85 t/s** | **≈100%（追平 4070）** |
| Xeon 6 + MRDIMM-8000 | 12ch / 800GB/s+ | 100+ t/s | 超越 4070 |

要点：
- 单用户流式问答由**带宽**主导；**并发多用户/批量入库**时核心数（96 核）才吃重
- 12 通道 DDR5 级平台为**数万元级**（单 CPU），4070 约 5000 元——**仅当服务器为既有资产时才划算**
- 平替建议：**二手 3090（24GB，带宽 936 GB/s）** 7B Q4 可达 150+ t/s，还能跑 32B，性价比高于 12 通道服务器

### 7.5 兰台场景搭配选型表

结合兰台各环节压力（入库向量化=低压力批处理；问答=延迟敏感；OCR/图片理解=最重）：

| 方案 | 硬件 | 本地模型搭配 | 适用 |
|------|------|-------------|------|
| A 入门演示 | 8GB 显卡 或 双通道 CPU + 32GB 内存 | qwen2.5:7b + bge-m3（视觉模型不启用或按需） | 个人/轻演示 |
| **B 标准推荐** | **RTX 3060 12G + 32GB 内存** | qwen2.5:7b + llava:7b / qwen2.5vl:7b + bge-m3（全功能） | 演示主力 |
| C 企业现网（既有服务器） | 8 通道 DDR5 Xeon/EPYC（64G+ 内存） | 7b 问答 + 3b 视觉或按需；并发 >8 用 96 核平台 | 内网多用户 |
| D 高性能/规模化 | 16~24GB 显卡（或 EPYC 12 通道） | 32B Q4 问答 + 视觉 7B；多实例负载分担 | 高并发、高质量 |

### 7.6 与演进路径的衔接（对照第五章）

- **阶段 1（单机增强）**：方案 B（3060 12G）作为标准配置基线；Docker Compose 部署时透传 GPU
- **阶段 2（服务化）**：多用户 → 核心数/多卡 + AI 网关层做模型路由与降级（云端兜底，如 MiMo/通义）
- **阶段 3（规模化）**：GPU 池（多卡/多机）+ 模型路由成本控制；纯 CPU 服务器仅承担 embedding/轻量任务

> 原则：**演示级不过度投资**（3060 12G 即全功能）；企业级优先利用既有 Xeon/EPYC 资产，增量需求再上 GPU。
