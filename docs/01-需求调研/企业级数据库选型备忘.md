---

## 一、背景

兰台当前向量与业务数据存储于 SQLite（单文件、numpy 全表余弦扫描），演示级（几十~几百切片）毫秒级够用。若作为**企业级知识库**（多用户、RBAC、海量文档、高可用、备份、鉴权），SQLite 在并发写、容量、运维、权限隔离上不满足，需要企业级数据库。

## 二、候选方案

| 方案 | 类型 | 优势 | 代价/注意 |
|------|------|------|-----------|
| **PostgreSQL + pgvector**（首选） | 关系库 + 向量扩展 | 复用企业现有 PG 运维/备份/权限体系；关系数据（文档元数据/用户/RBAC/对话历史）与向量同库、事务一致；HNSW/IVFFlat 索引支撑百万~千万级向量；SQL 生态成熟 | 亿级以上向量需调优分区/索引参数；pgvector 是扩展（官方维护） |
| **Qdrant** | 独立向量库（Rust） | 单机到分布式；性能好；**内置 BM25 稀疏向量**（契合档位 3 hybrid 检索）；API 简洁、部署简单（二进制/容器） | 业务数据仍需关系库；多一套服务运维 |
| **Milvus** | 独立向量库（分布式） | 十亿级向量；GPU 索引（IVF/HNSW）；RAG 生态集成好 | 组件多（etcd/minio 等）、运维重；小规模杀鸡用牛刀 |
| **OpenSearch / Elasticsearch** | 搜索库 + 向量 | 已有 ES 栈的企业直接复用；dense vector + BM25 混合检索成熟 | 向量性能弱于专用库；资源占用高 |
| Weaviate / Pinecone 等 | 独立向量库 | 生态完整 | Pinecone 为托管 SaaS（国内不可直连）；Weaviate 部署中等 |

## 三、选型建议（按场景）

| 场景 | 推荐 |
|------|------|
| 企业已有 PostgreSQL，向量 < 1000 万 | **pgvector**（增量成本最低：同库事务、复用 DBA/备份/权限） |
| 纯向量负载、规模大、要 GPU 索引 | **Milvus** |
| 规模中等、要混合检索（BM25+向量）且部署简单 | **Qdrant** |
| 已有 ES/OpenSearch 基础设施 | OpenSearch（dense vector + BM25） |
| 关系数据与向量分离、各自独立扩展 | 向量库（Qdrant/Milvus）+ 现有关系库 |

## 四、企业级落地的配套要素（与数据库选型并列）

1. **元数据过滤**：向量检索需按文档/分类/时间/权限（RBAC）过滤——pgvector 同库 JOIN 天然支持；独立向量库需冗余元数据或双写。
2. **混合检索**：BM25（关键词）+ 向量融合——pgvector 需配合 FTS；Qdrant 内置稀疏向量最省事。
3. **高可用与备份**：PG 主从/备份成熟；Milvus 分布式自带；Qdrant 需自行规划。
4. **鉴权与审计**：PG 行级权限可与 RBAC 联动；独立向量库需应用层控制。
5. **兰台接入路径**：`store.py` 的 `VectorStore` 抽象（add/delete/search/维度）为唯一存储入口——替换 = 新实现（pgvector 或 Qdrant 客户端）+ 配置项 `vector_store: sqlite|pgvector|qdrant`（即需求池 R108），业务代码不感知。
